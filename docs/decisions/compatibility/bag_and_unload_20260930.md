# 背包与卸装兼容修复（2026-09-30）

## 用户决定

卸装兼容普通和季节页面请求（optType 1/2），同一角色、同一槽位同时
解除普通 `equips` 和季节 `season_equips` 的穿戴关系。季节兽主的获取、
穿戴与养成暂未实现，类型 2 穿戴仍拒绝。客户端枚举的类型 2 是 BattlePass，
这里的合并卸装是用户决定，不宣称两种类型在官方语义中等价。

实机追加修复：`BagModule.UnloadAllEquip`（ARM64 0x19c6ef0）发送
`posIdx=-1`，表示同一角色全部槽位。服务端接受该哨兵并同时清空两套
穿戴关系，保留兽主实例及其他角色；重复空卸装成功且不写 snapshot。
0..5 仍只卸指定槽位，其他槽位值拒绝。HeroUpdate、EquipUpdate 在成功
回包前发送，因为客户端成功回调立即读取穿戴状态。

## 库存移除

客户端物品更新 553 不足以删除背包格子，使用 554 的 `ids` 显式移除。
数据库零数量行作为持久化移除记录保留，回包过滤零数量；后续推送可重复
移除，即使调用方只发送第一条推送也不会丢失记录。回填物品后不再移除。
永久开放头像框仍按原有规则投影到库存，排除在移除名单之外。
不在推送构造中 DELETE 或额外 commit，保持奖励、receipt 的事务边界。

永久开放的头像、场景目录统一 rankId=1，按客户端 rankId==0 判新规则
消除外观红点。该规则不提供新图标逐项未读提示。

## 道具与宝石

`tools/analysis/build_bag_client_catalog.py` 从官方 2.4 APK 的 ResourceManager
选择 Item/Gift/Language/Recipe/JewelBase，经 RSA/XOR 解码、严格 protobuf
边界校验导出：218 个 Used 道具、234 个 Gift、143 个配方、115 个宝石。
原始输入与哈希分别记录在 analysis/dp_client/raw、analysis/bag_client/raw。

固定奖励完整发放；随机奖励按客户端权重逐次抽取；自选奖励校验客户端
selectedItemIndexList；每次消费的全部组须有效，禁止扣款后跳过不完整组。
随机表中的零数量候选保留为空结果并消耗，避免失败回滚形成免费重抽。
徽章盲盒采用一次权重抽取的兼容语义（候选与权重取客户端数据，官方
服务器实现未恢复）。角色重复补偿复用现有抽卡原型规则。
兽主礼包星级仅从客户端道具/GiftShow 的 N★文字确认，经现有实例工厂
创建并返回 rewardEquip；不改变战斗 887/outsideItems 的验证及预算。

144/147 宝石合成按 Recipe 的材料、金币、产物执行，材料只能来自背包，
已镶嵌宝石不会被消费。操作、发奖、receipt 共用 SAVEPOINT 事务，重放
使用原结果；成功回调前推送背包和玩家数据。725/726 为已拥有角色的
宝石提示确认，保存幂等已读记录，避免未知协议无响应。

## 边界

测试只使用临时数据库，未定向修改 active DB。卡池、商店限购、好感成本、
兽主强化公式保持现有实现。当前 main 的永久外观开放及 DP 新实现保留。
