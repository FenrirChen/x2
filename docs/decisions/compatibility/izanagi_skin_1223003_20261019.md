# Decision
静影糜株 是伊邪纳岐（hero 1030）的 5 星觉醒外观，编号 Appearance 1223003。官方权威
表仍保留 1223003 行、商品货位 1980045 与显示名，但配套美术资源在官方客户端里被当作
废案剔除，所以货位一上架就是空白卡片 / 空白详情页 / 无头像。Revival 侧整条恢复：

- 服务端把货位 1980045 加回
  [appearance_shop_catalog.json](../../../src/x2server/data/appearance_shop_catalog.json)，
  货位数 27 -> 28（[appearance_shop.py](../../../src/x2server/player/appearance_shop.py)
  的启动断言同步）。
- 客户端用 [tools/patch_izanagi_skin.py](../../../tools/patch_izanagi_skin.py) 把 5 份资源
  补回参考包，产出 5 个可直接替换的资产：`9c7fdb35…`（载体立绘 + 卡片）、
  `2af4a6e8…`（图集头像）、`globalgamemanagers`（资源容器）、`2c6eecbf…`
  （Appearance 表）、`5c993e69…`（UnitBase 表）。

# Reason
只补服务端货位不够，客户端三个容器键和两行表数据都缺：

- Appearance 1223003 引用 `Icon` = `SkinHead01/Hero_Icon_103003`、
  `HalfDrawing` = `UIAltas/HeroIcon_H/Hero_Icon_103003_H`、
  `ShowImg` = `UIAltas/SkinDrawing/SkinDrawing_1223003`。这三个资源键在参考包的
  `ResourceManager.m_Container` 里都不存在，所以卡片、头像、详情页整图全是空引用。
- Appearance 1223003 的 `SpineShow` 还是 `SpineModle/SP_103003`，它指向只有 spine
  残件、没有 atlas 的目录；详情页走 spine 分支时空引用，把界面初始化截断（顶栏
  返回按钮都绑不上）。清空该字段后回落到 `RawImage` 分支，读 `ShowImg` 立绘。
- Appearance 1223003 的 `MainPaintingScale` 是 110，而这张原画 1980x2048 比常规皮肤
  大约 21%，主城立绘会溢出；改成 55 抵消。
- UnitBase 1030 的 `AppearanceList` 只有 `[1223001, 1223002]`，缺 1223003，神格详情
  的外观列表会少一项。

# Scope
客户端 5 处改动，全部只读写参考包、不覆盖输入：

- A. 载体 `9c7fdb35…`（与立绘 1222703 同文件）：追加 Texture2D `pid 1000`（原画整图
  RGBA32）+ Sprite `pid 1001` `SkinDrawing_1223003`（整图）+ Sprite `pid 1002`
  `Hero_Icon_103003_H`（竖版卡片框 460x1045，与 1001 共用同一张贴图）。既有 `pid 1/2`
  原样保留。卡片框取整幅坐姿取景，与姊妹皮肤的竖版卡片一致。
- B. 图集 `2af4a6e8…`（skinhead01，34 张头像）：追加 Texture2D `pid 100`
  （150x150 RGBA32）+ Sprite `pid 101` `Hero_Icon_103003`。原贴图是压缩格式
  （TextureFormat 47），为不重编码压缩纹理，新头像另起一张 RGBA32 贴图；原贴图与
  34 张 Sprite 一律不动。
- C. `globalgamemanagers` 的 `ResourceManager.m_Container`：新增
  `uialtas/skindrawing/skindrawing_1223003` 与 `uialtas/heroicon_h/hero_icon_103003_h`
  （各 2 条，指向 A 的 `pid 1000+1001` / `pid 1000+1002`），并在
  `uialtas/altas/skinhead01` 组（原 35 条）末尾补 1 条指向 B 的 `pid 101`。容器键全
  小写且严格按路径有序：运行时把请求串转小写后做区分大小写的二分查找，大写键或错位
  插入都会查不到并连带破坏邻近资源。
- D. Appearance 表 `2c6eecbf…` 的 1223003 行：字段 15 `SpineShow` 清空，字段 29
  `MainPaintingScale` 110 -> 55。
- E. UnitBase 表 `5c993e69…` 的 1030 行：字段 48 `AppearanceList` 追加 1223003。

两张表都是 Unity TextAsset：前 128 B 是 RSA 头，其余是「位置异或」后的明文。D 会缩短
明文、E 会加长明文，两者都不是等长替换，所以工具保留 RSA 头、只重加密密文尾部，再用
UnityPy 重建该 SerializedFile 条目。A/B/C 是往既有 SerializedFile 追加对象，同样整文件
重建。工具自检覆盖：像素逐字节回读、四边形网格自洽、新键的 pathID 与有序性、表字段
往返。参考包上产出的 5 个资产 SHA-256（未打补丁的输入）：

新增 Sprite 的四边形网格照抄原版约定：4 顶点 / 20 B 步长（位置 float32x3 + UV

取图，原版所有 Sprite 的 UV 都是 0）。

# Official
NO（官方权威表保留 1223003 行、货位 1980045 和显示名，但官方客户端已把配套立绘 /
头像 / 卡片资源剔除；补回资源是 Revival 的兼容决定，原画来源见 Notes）

# User-authorized
YES（USER_DECISION，2026-10-19）

# Usage
```powershell
python tools\patch_izanagi_skin.py --apk <reference.apk> --output <dir>
python tools\patch_izanagi_skin.py --apk <reference.apk> --skin <原画.png> --output <dir>
```

输出目录里是可直接替换同名 zip 条目的 5 个资产（文件名 = 原 zip 条目名 + `.bin`），外加
`patches.json`（条目 -> 产物路径）和 `audit.json`（每处改动明细）。替换后必须用本地开发
密钥重新签名才能安装；工具自己不做签名，也不安装到设备。

# Notes
- 参考包必须是含这 5 个摘要（`9c7fdb35…` 等）的原始基包；工具只读入参考包、只往
  `--output` 目录写产物，不就地改写输入，资源布局不符时抛错停止。
- 默认原画 `tools/assets/izanagi_skin_1223003.png`（1980x2048 RGBA），两张对照预览图
  `izanagi_skin_1223003_preview_card.png`（卡片：左=现役皮肤 右=静影糜株）与
  `izanagi_skin_1223003_preview_head.png`（头像）供人工核对。
- 原画是否等同官方静影糜株原图未确证：该 PNG 来自外部立绘合集，只能确证 1223003 的
  官方名称与编号，不能确证图像出处。行为与命名对齐官方表，图像来源按兼容素材标注。
- 不随 PR 提交改好的 `.bin` 载荷（约 42 MB），符合 `revival_client/README.md`
  「APK / 构建产物不入 Git」；老大侧拿到工具 + 原画后自行产出并重签。
