## 推荐实施路线

1. 先补当前活动的客户端资源引用：保留原版预制体布局及按钮，将背景图绑定到既有背景 AdvancedImage。使用 APK 内已有 Sprite，不修改玩法协议。
2. 优先核对本期官方背景的资源名和图像；如果仍无法确认原绑定，可明确采用街市烟花图作为兼容背景，不能将候选图宣称为已恢复的官方原图。
3. 修补工具必须校验源文件摘要、节点名称、组件脚本和空引用；遇到不同版本停止。输出独立文件，保留原 APK，禁止直接覆盖分析源。
4. 优先改预制体序列化资源；增加正确的外部文件引用和 Sprite PPtr。需要验证资源文件仍能被 UnityPy 重新读取、已有资源依赖仍可解析。避免仅硬编码运行时内存偏移。
5. 复用已有 APK 打包与签名流程，保持原包名和签名来源。先在测试模拟器升级安装并保留数据，确认当前安装签名可升级后再安装。
6. 验证主界面背景可见、文字可读、宽屏裁切、分享页面及所有子活动进入/返回；查看 Unity 日志，排除遮挡点击与资源加载异常。通过后才发布新的客户端包。

## 其他活动与服务端边界

不把首期的发现推断为其他七期同样原因。应逐期建立「页面 → 背景节点 → Sprite/Texture → 文件」清单，区分空引用、缺文件、动态图路径错误和正常的纯色设计。动态图如果确实来自服务器字段，可以修服务端映射；固定预制体的空引用需要客户端修补；缺失图片则还需要找到原始资源或明确选择兼容图。

通过 HTTP 提供 PNG 本身不能让此页面显示背景：客户端当前没有读取这个 URL 的调用。是否可以通过现存热更新通道发放预制体，尚未验证；没有验证前按需要更新 APK 处理。
