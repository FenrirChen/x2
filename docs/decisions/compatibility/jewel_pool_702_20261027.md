# Decision
22702「莫格尔祖母绿」是绮石许愿池 22700-22709 里唯一一个「6★ 宝石姬本体和池子
表行都在官方数据里、但客户端三张图和引用行缺失」的池子。官方 `DrawParam` /
`DrawRules` 仍保留 22702 行，JewelBase 1251004/1251005/1251006 也早已存在，其中
`f12` 就是 `UIAltas/Drawing/Jewel/BaoShiJi_2`；但参考包的资源容器里没有这张立绘、
没有 `GuangGaoTu_Cover702` 横幅、也没有 `ChouJiang_Tab702` 页签，三个池表挂点
（`DrawParam.f35` 预览、`DrawRules.f3` UP / `f5` 列表、`Gift 750106/750108` 权重）
同样缺失。Revival 侧整条恢复：

- 服务端把 1251004 加回
  [wish_catalog.json](../../../src/x2server/data/wish_catalog.json) 的 22702
  `common`（权重 52）与 `top`（权重 496），与客户端 Gift 表逐项一致。
- 客户端用 [tools/patch_jewel_pool_702.py](../../../tools/patch_jewel_pool_702.py)
  把三张图和三条容器键补回参考包，并修好三张池表，产出 7 个可直接替换的资产：
  `11f10428…`（立绘 `BaoShiJi_2`）、`2f27eb21…`（横幅 `GuangGaoTu_Cover702`）、
  `83629c10…`（页签 `ChouJiang_Tab702`）、`globalgamemanagers`（资源容器）、
  `794cf065…`（DrawParam）、`109c23e5…`（DrawRules）、`97f907f9…`（Gift）。

# Reason
只补服务端权重不够，客户端三处资源、三张表都缺：

- `BaoShiJi_2` 立绘、`GuangGaoTu_Cover702` 横幅、`ChouJiang_Tab702` 页签在
  `ResourceManager.m_Container` 里都不存在。许愿页卡面/横幅走
  `GameAPI_GetSpriteByAltas`，本 build **没有兜底**：名字取不到就 `overrideSprite = null`，
  画出来是白卡 / 空白横幅 / 缺页签（[CURRENT_STATUS.md](../../CURRENT_STATUS.md)
  的「卡池预览图」条记录了同一渲染链）。
- `DrawParam` 22702 没有 `f35`（详情页预览宝石），「查看详情」的 UP 卡池菱形图缺项。
- `DrawRules` 22702 没有 `f3`（UP 宝石），`f5` 列表也没有 1251004；客户端据此画
  UP 标记和卡池宝石格，服务端抽取则按 catalog 的 `top` / `common` 组。
- `Gift 750108`（十连 top 组）和 `Gift 750106`（单抽/普通组）都没有 1251004 的
  权重行，客户端展示的出率和实际抽取结果都对不上。
- 权重口径照同族单 UP 池 22701：`top` 496 / 992 = 50%（22701 是 51.6%）；整池
  `common` 52 / 10074 = 0.516%（22701 是 0.52%）。1251004 在 `common` 里是中档
  6★（16）的 3.25 倍、低档（13）的 4 倍，与「测试服独有 6★ 宝石姬」定位一致。

# Scope
客户端 7 处改动，全部只读参考包、不覆盖输入：

- A. 载体 `11f10428…`（与 `BaoShiJi_3` 同文件）：追加 Texture2D `pid 1000`
  （688x828 RGBA32）+ Sprite `pid 1001` `BaoShiJi_2`（整图，4 顶点四边形网格）。
  既有 `pid 1/2` 原样保留。该立绘同时被 JewelBase 1251004/1251005/1251006 共用，
  本池只引用 1251004。
- B. 载体 `2f27eb21…`（与 `Cover709` 同文件）：追加 Texture2D `pid 1000`
  （1404x592 RGBA32）+ Sprite `pid 1001` `GuangGaoTu_Cover702`。
- C. 载体 `83629c10…`（抽奖页签图集，原 59 张 Sprite）：追加 Texture2D `pid 1000`
  （220x68 RGBA32）+ Sprite `pid 1001` `ChouJiang_Tab702`；原有 59 张一律不动。
- D. `globalgamemanagers` 的 `ResourceManager.m_Container`：新增
  `uialtas/drawing/jewel/baoshiji_2` 与 `uialtas/draw/guanggaotu_cover702`（各 2 条，
  分别指向 A/B 的 `pid 1000+1001`），并在已有的 `uialtas/altas/draw` 组（原 60 条）
  末尾补 2 条指向 C 的 `pid 1000+1001`。参考包上容器 10049 -> 10055 条。容器键全
  小写且严格按路径有序：运行时把请求串转小写后做区分大小写的二分查找，大写键或错位
  插入都会查不到并连带破坏邻近资源。`m_FileID` 从同目录的姊妹键
  （`baoshiji_3` / `cover709` / `draw`）解析并校验外部文件名，不写死索引。
- E. DrawParam 表 `794cf065…` 的 22702 行：字段 35 插入 1251004（紧随 `f33`）。
  字段 36（预览位置）继续留空：22700/22701 的 `f36` 与 JewelBase
  `PaintingPosition × 100` 不成比例，语义未明，硬填会让预览立绘偏框，交客户端
  默认值（与 range60 实机复核结论一致）。
- F. DrawRules 表 `109c23e5…` 的 22702 行：字段 3 插入 1251004（紧随 `f2`），
  字段 5 列表头插入 1251004。
- G. Gift 表 `97f907f9…`：750108 的字段 3/4 头部插入 496 / 1251004；750106 在
  1251014 锚点前插入 52 / 1251004（权重与物品保持同索引对齐，1251004 落在第 16
  个位置）。

三张表都是 Unity TextAsset：前 128 B 是 RSA 头，其余是「位置异或」后的明文。E/F/G
都会加长明文，所以工具保留 RSA 头、只重加密密文尾部，再用 UnityPy 重建该
SerializedFile 条目；A/B/C/D 是往既有 SerializedFile 追加对象 / 容器项，同样整文件
重建。工具自检覆盖：像素逐字节回读、Sprite 绑定与四边形网格自洽、`m_Container`
全小写且有序、新键 pathID、目标行往返、非目标行逐字节不变。参考包

# Usage
```powershell
python tools\patch_jewel_pool_702.py --apk <reference.apk> --output <dir>
python tools\patch_jewel_pool_702.py --apk <reference.apk> --art-dir <目录> --output <dir>
```

输出目录里是可直接替换同名 zip 条目的 7 个资产（文件名 = 原 zip 条目名 + `.bin`），
外加 `patches.json`（条目 -> 产物路径）和 `audit.json`（每处改动明细）。替换后必须用
本地开发密钥重新签名才能安装；工具自己不做签名，也不安装到设备。

# Notes
- 参考包必须是含上表 7 个摘要的原始基包；工具只读入参考包、只往 `--output` 目录写
  产物，不就地改写输入，资源布局不符时抛错停止。默认图在
  `tools/assets/jewel_pool_702/`：`baoshiji_2_688x828.png`（SHA-256
  `d2da62220bf08e5e522776648af5ae48c7573347125409a9d03f82dff0e53b66`）、
  `cover702_1404x592.png`（`fb8b7cb81d4730576fef7dffe007373099f9b003db0a15c8ffb37049b99f80a9`）、
  `tab702_220x68.png`（`068f31ac2f0b7b2af5b02426280efbec08f5c8c172a5aa24880baa775a7ad23f`）。
- 三张图是本工程自制兼容素材。官方客户端没有 `BaoShiJi_2` 立绘、`Cover702` 横幅和
  `Tab702` 页签；`BaoShiJi_2` 的官方名称/编号只能从 JewelBase 1251004 的 `f12` 确认，
  图像出处无法确证，按兼容素材标注。立绘同时服务 1251004/1251005/1251006。
- 已实机复核：2026-10-27 `range60-pool702` 起，22702 卡片/横幅/页签/详情页 UP 图标
  正常；2026-10-29 `range61-jewelicon` 补齐了 `Ico_Img_1251004` 的 4★ 菱形图标并
  复核通过（见 [CURRENT_STATUS.md](../../CURRENT_STATUS.md)）。**4★ 图标不属于本
  PR**：它在 range61 单独出包，需要 `d1c7bde5…` Gemstone 图集 + `uialtas/altas/gemstone`
  键；本 PR 只带池子三张图 + 三张表。
- 服务端 `wish.py` 在上游分支把 10 个绮石池全部下发（没有本服那份
  `UNRENDERABLE_POOLS` 过滤），所以本 PR 只补 catalog 的 1251004 权重，不动
  `wish.py`；本服「从 UNRENDERABLE_POOLS 移除 22702」属于本服轮换实现，不随此 PR。
- `DrawParam.f36` 继续留空是已知限制：它的语义（预览位置）没有反汇编证据，22700/
  22701 的取值也不能按 JewelBase `PaintingPosition × 100` 对齐；填错会让详情页预览
  立绘偏框。若后续取证确认，再补这一行。
- 本 PR 附带成品资产包
  [tools/assets/jewel_pool_702/ready/](../../../tools/assets/jewel_pool_702/ready/)：参考包
  `X2-Revival.apk` 上生成的 7 个 `.bin`（合计 30,366,080 B），以及 `manifest.json`
  （条目 -> 文件名）、`audit.json`（工具自检明细）、`README.md`。文件名 = 原 zip 条目
  名 + `.bin`，覆盖 APK 的 `assets/bin/Data/<原条目名>` 后重签即可打包；SHA-256 与上表
  「输出」列一致。
- **基包一致性**：成品是在参考包（输入摘要见上表）上生成的。若基包不是同一份，或已经
  叠加了其它会改 `globalgamemanagers` / `DrawRules` / `Gift` 的补丁，直接整文件覆盖会
  把这些补丁一起盖掉 —— 这种情况必须对基包重跑工具
  `python tools/patch_jewel_pool_702.py --apk <基包> --output <目录>`，不要用成品替换。
- 仍不提交 APK 与签名材料：[revival_client/README.md](../../../revival_client/README.md)
  明确「APKs, signing keys and runtime logs are local build artifacts and are excluded
  from Git」，`.gitignore` 也忽略 `*.apk`；成品 `.bin` 只替换条目，不含签名。
- 验证命令：`python -m pytest tests\unit\test_patch_jewel_pool_702.py tests\unit\test_wish.py -q`
  （16 + 14 项通过）。工具端到端在 `client/X2-Revival.apk` 上跑通：3 个载体与
  DrawParam 和 range62-jisha 逐字节一致；DrawRules/Gift 的目标行与 range62 一致，
  其余行保持不变（range62 还带别的池/礼包修补，所以整文件哈希会不同，属正常）。
