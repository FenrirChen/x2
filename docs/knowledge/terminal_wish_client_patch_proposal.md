# 心愿客户端最小补丁方案（待用户授权）

目的：解决接取后连续在线跨零点且没有领奖时，isAnalyse=true导致次日新候选无法进入选择页的边界。

范围：仅FavorWishModule.OnReceiveFavorWishMsg(0x18b9b6c)在接收服务器心愿列表时清除过时的isAnalyse缓存，页面由服务端TaskStatus判断；不修改战斗、账号、抽卡、任务奖励、APK资源图片或服务器地址。

具体变化：在进入列表替换逻辑时执行`this.isAnalyse=false`，保留原有清空/填充/排序列表与UI刷新。ARM64调用中x19为this，字段偏移0x28；需要以原指令校验、保留被搬移指令的代码跳板加入`strb wzr, [x19, #0x28]`，不能直接覆盖仍使用的原指令。地址仅对当前已核对2.4版本成立，打包前必须核对两份APK的libil2cpp.so方法字节和已有补丁。

预期页面行为：

| 服务端列表 | 修复后页面 |
| --- | --- |
| 未分析，空列表 | 开始分析 |
| 已分析，8 条 WAITING 候选 | 选择页，需从候选中选满三个确认 |
| 已接取START/REWARD任务 | 任务页，领取符合条件的奖励 |
| 已领取FINISH任务 | 完成状态任务页 |
| 连续在线跨日后新WAITING候选 | 选择页，不沿用昨天的isAnalyse |

验证项：首次分析/确认/领奖、关闭重开、重登、连续在线跨零点且零次领奖/部分领奖/全部领奖、接取确认后自动查询、已有APK活动和试用补丁保持原效果。

如获授权，更新本地开发、远程服务器两份APK，保持各自服务器地址和原有已批准补丁，先校验和打包，再由用户手动验收。本方案尚未修改或生成任何APK。
