# 随机三星单个新角色结果弹窗（2026-10-14）

用户反馈：反复存档导入后前三次开启有结果，随后开启没有结果，无玩家日志可供核对。

已确认一处与该表现一致的客户端协议缺陷；不能断言所有玩家每次“无结果”均由同一个原因触发。

## 客户端证据
UIAPI.ShowGetAwardItem RVA 0x134bccc：rewardItem 和 transformHero 各只有一条时（0x134bf94–0x134bfd8），若不是重复转换，进入单个角色展示。

0x134c0d0 取 TransformHero 第 0 条；0x134c0e0 直接取 heroId 字段（对象 +0x10）；0x134c0f8 将它传给 ItemManager.GetItem；0x134c100–0x134c108 非空检查/读取 ItemType，然后 ItemType=15 时打开 UI_GetHero。这里没有“+1210000”的转换，所以协议字段名 heroId 实际要求角色卡物品 ID。

此前 grant_bag_rewards 发 heroId=1005，物品表无该 ID（只有角色表有）；正确值是 1211005。单个新角色进入该分支会查到 null。重复角色奖励通常包含角色卡显示条目、碎片、票据三个 rewardItem，不进入单条分支，可能正常显示。这可以解释“前几次正常、随后无结果”的随机性，但次数本身不是限制。

## 修改
- 背包奖励的 transformHero.heroId 下发完整角色卡物品 ID。
- bag_reward_view 规范化旧回执里的 1000–1999 角色编号，重传不重新扣除道具、重抽或补发。
- 历史礼包恢复同时识别旧角色编号及新完整物品 ID，避免升级协议后丢失修复能力。
- 保留上一轮 rewardItem 按物品 ID 合并，以及 transformHero 逐抽记录。随机候选和权重不变。

## 验证
依据真实客户端分支和现有物品表建立契约检查：旧单个新角色回包确定查不到 Item，修正回包可查到对应角色卡 ItemType=15。

实际 SaveManager 导出/导入同一完整存档，前三次选择已有角色、第四次选择新角色，每次沿 EconomyService 的真实使用请求入口开盒，均完成正确扣除与发奖；重复请求不再次扣除。另覆盖跨账号连续四次导入、全部 11 种新角色、批量新/重复混合、旧回执规范化和有明确记录的缺失角色恢复。

无玩家日志时，不应仅凭“没弹窗”给已到账角色再次补偿。现有恢复以持久回执和发奖账本为依据。本轮无需修改 APK。用户仍需手动验收真实弹窗。
