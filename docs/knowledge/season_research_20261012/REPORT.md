# 赛季功能内容、保留程度及恢复可行性

2026-10-12。范围：原 Android 2.4 APK、Il2CppDumper 元数据、libil2cpp 原生代码，以及当前 `D:\demo\x2\x2_revive_workspace` 服务端源码。这里只研究并导出证据，没有开放赛季或修改运行中的服务端。

**结论：可以恢复，客户端保留了主要玩法、配置和专属界面；服务端需要新增完整赛季业务。不能只把活动列表中的赛季设为开启，就认为已修复。**

## 已找到的三套赛季

| 赛季 | ActivityID | BattlepassID | 客户端结构 |
|---|---:|---:|---|
| S0 起源悖论 | 74001 | 10000 | ActivityGroup16；第一套赛季界面 |
| S1 月相明暗 | 74004 | 10001 | ActivityGroup23；第二套赛季界面 |
| S2 暇裕时光 | 74007 | 10002 | ActivityGroup34；第三套赛季界面，含独立挑战配置 |

三个活动都是 `ActivityType=55/E_BattlePass`，原配置的 `OpenLever=20`。原表时间和周编号已经是旧日历，必须建立新的服务器期次并统一转换，而不能直接把旧时间交给今天的客户端。

名称依据：S0 `BattlepassName=740011` 的语言文本直接为“起源悖论”；S1/S2 名称从通行证、赛季商店、徽章等原语言文本交叉核对，本次语言表没有找到740041、740071的对应文字。S0通行证描述还保留“蚀之世跃迁”这一称呼，不将它误列为第四套已确认赛季。

证据：[活动及关联统计](linkage_summary.json)、[Battlepass原表](tables/battlepass.json)、[赛季语言原文](season_language.json)。

## 赛季包含哪些内容

| 内容 | 客户端保留的逻辑及依据 | 恢复判断 |
|---|---|---|
| 赛季大厅与章节 | `BattlePassModule` 有独立主界面、章节、任务、商店、天赋、神迹、排名跳转 | 可恢复；先补初始化和活动同步 |
| 试炼梦境/刷取关卡 | 原语言明确100阶、难度与产出递增；SeasonConfig有门票、随机候选关卡和权重 | 可恢复；需扣票、选关、掉落、结算、解锁闭环 |
| 终极梦境/挑战 | 原语言明确无掉落、不耗因果或门票、逐阶挑战，通关30阶以上可计排名；S2有100条独立挑战配置 | 可恢复；必须与刷取模式分开处理 |
| 赛季凭证 | 先锋/进阶/精英三档图标，等级经验、分档奖励、购买等级、签到、历史查询 | 表和协议保留；进阶/精英开放方式需由运营确定 |
| 赛季任务与活跃度 | 固定/随机任务、刷新、周经验上限、赛季周活跃度；条件包含战斗、Boss、商店、门票等 | 可恢复；需接入真实事件计数和周期 |
| 成就、里程碑 | 分类总览、详情、成就领奖、积分领奖、历史里程碑与徽章 | 可恢复；需前置、进度、领奖幂等 |
| 赛季天赋 | 15条天赋、9个天赋组，等级、属性、重置；模块有剩余点数 | 配置保留；点数来源、费用和叠加需追踪执行路径 |
| 赛季神迹 | 收集列表与战斗效果配置，成就包含收集不同数量的神迹 | 可恢复；收集、查询、效果及期末清理需一起做 |
| 魂器蚀化 | 五槽属性池、数值权重、消耗材料、宝石效果；有专门操作协议 | 可恢复；随机、扣料、属性下发与重置缺少服务端实现 |
| 赛季兽主与配装 | 兽主带SeasonId；玩家有seasonEquips和独立赛季属性计算；文本明确期末标签消失 | 可恢复；普通与赛季配装、获取标签、战斗使用和期末转换必须一致 |
| 排名与结算奖励 | 段位、当前/全部段位、角色及凭证等级排名界面，段位和排名区间奖励 | 配置保留；排名统计、快照、周期结算和同分规则需实现 |
| 指定角色加成 | S2 BattlepassUnit有3个角色的PassiveID和显示数值 | 可恢复；应使用原被动链，不能只修改界面数字 |

语言证据中明确的规则包括：

- Key13420064：试炼梦境共有100阶，难度和产出递增。
- Key13420070：终极梦境没有掉落，也不消耗因果和门票。
- Key13420075：终极梦境需逐阶挑战，不能跳阶。
- Key13102664：通关终极梦境30阶以上可以计入排名。
- Key210134：赛季关卡掉落兽主附特殊标签，可用于终极梦境，赛季结束后标签消失。
- Key12381062等：魂器蚀化效果会在赛季结束时清空。

这些是保留的客户端文本规则；实际执行的参数和序列仍需核对消费方法。S0/S1与S2的关卡和界面不同，不能把S2全部逻辑强行套给前两期。

## 保留的数据有多少

已从原APK提取并解码：

- Battlepass：3条。
- SeasonConfig：400条，S0/S1/S2刷取配置各100条，S2挑战配置100条。
- BattlepassLevel：1300条；Task：108条；Achievement：212条。
- Talent：15条；TalentGroup：9条；Artifact：5条；Miracle：3条；Unit：3条；Milestone：4条。
- Rank：81条；RankReward：87条；ExRankReward：13条；Award：12条。

SeasonConfig去重引用了2395个SectionID，**全部能在SectionTable中找到，类型均为20/E_Battlepass**。这是随机候选关卡条目数量，不是玩家要连续通关2395阶。

本次检查的凭证等级、任务、成就、阶层奖励及排名奖励共引用1678个去重GiftGroup，全部存在于Gift原表。这个检查证明奖励组有配置，不证明每个奖励都已经在服务端正确执行，也不涵盖所有商店商品的库存配置。

资源索引中的32个 `ui/` 且名称含battlepass的资产都存在于APK。原生 `GetBattlePassMainPrefab` 明确引用 `UI_BattlePass_Main`、`UI_BattlePass_Main2`、`UI_BattlePass_Main3`；章节选择引用 `UI_MapChoose/2/3`。**没有发现必须先重做赛季UI才能恢复的依据**；但本轮没有实际打开全部页面或核验全部贴图、场景依赖。

证据：[表来源、哈希和行数](table_manifest.json)、[配置关联检查](linkage_summary.json)、[UI资产存在性](battlepass_ui_assets.json)、[原生方法索引](native_methods.json)、[原生字符串引用](native_string_references.json)。

## 当前服务端支持程度

当前主要业务缺口：

1. 没有专门的BattlePass/赛季服务及对应完整协议注册。玩家服务源码中Battlepass主要只出现在通用战斗类型和代币映射中。
2. `messages/lobby.py`、`player/appearance.py` 已处理SeasonIcon头像查询与穿戴，**这是外观子系统，不等于赛季玩法已实现**。
3. `player/battle_entry.py` 只将Type20命名为Battlepass，仍走通用关卡入口；没有恢复SeasonConfig门票、随机选关、期次、挑战规则。
4. `player/equipment.py:260` 明确注明赛季兽主获取/穿戴未实现；只能清理普通/赛季穿戴关系。装备生成中的seasonId仍为0。
5. `player/battle_bonuses.py` 没有赛季天赋、赛季神迹、魂器蚀化、角色赛季加成的完整下发。
6. 现有主题活动轮换与赛季配置并非同一套业务；需要先区分期次和状态，不能复用主题活动全局进度字段造成相互覆盖。

其中普通战斗、奖励发放、任务事件、存档持久化可以复用基础组件，赛季规则仍需单独实现。当前状态应视为“主要链路缺失”，不能以战斗Type20已识别作为可上线依据。

证据：[赛季消息ID](season_protocol_ids.json)、[凭证相关消息ID](battlepass_protocol_ids.json)、[类字段声明](season_fields.json)、[模块元数据](battlepass_module.json)、[原生方法](native_methods.json)。类字段声明不是已经验证过的protobuf schema；必须再核对Serialize/Deserialize方法。BattlepassLevel中出现unknown_field_10也应继续追踪，不能把它随意丢弃。

## 怎样修复，何时才算闭环

建议首先恢复一套完整赛季，**S2暇裕时光优先**：它保留独立刷取/挑战配置、专属兽主与角色加成，便于把完整机制做通。随后再适配S0/S1各自的界面与规则。这个顺序是实现建议，本轮没有更改开放活动。

1. 统一赛季状态：活动ID、BattlepassID、当前期次、开始/结束/领奖截止、周序号、入口解锁。
2. 补初始化、基础查询和推送，再实现刷取/挑战的选关、消耗、掉落、存档、结算、下一阶解锁和断线恢复。
3. 接入任务、签到、凭证经验、等级奖励、成就及商店；奖励与扣料必须事务化，重试不重复发放。
4. 接入兽主标签/配装、天赋、神迹、魂器蚀化、指定角色加成；界面面板与战斗快照必须一致。
5. 完成排行榜统计、奖励快照与邮件补领、历史里程碑、跨期迁移、完整存档导入/导出。
6. 验证同一赛季再次开放：使用独立instance_id存储进度，不能仅用ActivityID；旧期结算可追溯，新期任务/门票/临时属性不串期。

原语言明确期末标签消失和蚀化清空，但普通兽主保留、卸装转换、旧排名徽章及可补领奖励的具体迁移策略仍应逐项核对，不能以删除整个赛季状态代替。

上线前必须覆盖：新号首入、旧号再入、活动与赛季共存、通关后进度推送、重复结算/领奖、重连、周切、赛季结束、同赛季第二轮、存档迁移、远程部署。按用户此前要求，手动验收由用户进行，服务端自身需先完成协议及状态回归。

## 仍需要确定或继续逆向的部分

- 新日历：开放顺序、每期长度、周切、结算/补领奖时间。旧日期不能原样复用。
- 先锋/进阶/精英凭证如何获得，购买等级和任务刷新如何收费。原价表/商品ID不代表现服务器已有相应发放链。
- 赛季掉落预算、装备标签与普通装备转换。既有预算明确未为Battlepass套用100%=3000百分比政策，不能悄悄沿用主题活动规则。
- 天赋点来源/重置、神器蚀化随机与最终叠加、角色加成范围、排行榜同分及时间规则，需要继续核对原生代码。
- 商店商品的物品/数量/库存需逐项关联；只找到ShopGoodsGroup价格不能假定全部商品配置齐全。
- S1/S2部分名称语言键和unknown_field_10、场景资源依赖、热更新优先级需要补核验。

**可行性判断：主要内容有恢复依据，实施重点在服务端，预计大部分功能能用现有APK实现；是否完全无需APK调整，需要完成上述消费链和实机入口验证后确认。**
