# 活动剧情重复播放：原生刷新点与轮换隔离

## 真实复发

2026-10-12 13:12，玩家1在当前阏逢敛遗活动反复发送740/C2L_ActivityPreNotic，均收到code10，却仍重复播放剧情。SQLite中的本期pre-notice[72040]与响应回执均为1791766379（北京时间08:52:59），与本地审核日历起点相同。没有本次Unity空引用堆栈。

此前修复只将旧完成时间抬到活动起点，并将重复确认变为成功，没有模拟客户端的真实刷新判定。

## 原生证据

BaseActivityModule.Show调用ActivityNoticeModule.CheckActivityPreNoticeCanAward(0x1335b20)。后者读取已确认时间，调用ServerTime.GetRefreshTime(0x3e5227c)，当当前时间达到刷新点且预告故事仍在有效日期内时重新播放。

GetRefreshTime的ARM64整数运算等价于：

```
refresh = timestamp + 86400 - ((timestamp - 18000) % 86400)
```

当前服务器使用Unix秒，因此这是UTC05:00、北京时间13:00的下一个刷新点，不是北京时间零点。08:52的旧完成时间在13:00失效，解释了13:12的反复剧情。证据输出保存在忽略的runtime/activity_preview_refresh_time_20261012.txt及其他activity_preview_*反汇编中。

## 修复

当前恢复的预告每期只有一段剧情。本期已完成时，查询/重复确认将确认时间抬到当前原生刷新窗口起点及本期起点中的较大值，维持完成标记；未完成仍返回0。不修改全局业务日切，不再次发奖励。

缓存预告查询和QueryActivity重新读取实时状态；已成功的740/628回执保留原奖励数据，只更新完成确认时间，防止旧回执恢复过时状态。日月盈仄的两个确认入口共享完成状态，重复剧情确认成功但不再发奖；未完成且已过预告开放窗口仍拒绝。

## 重复轮换

完成状态、事件、奖励来源均带ActivityPeriod.index。七期轮换沿用历史状态槽0/1/2/4/5/6/7，每个完整轮次跨8个状态槽，不能把下轮第一个活动存成旧日月盈仄的槽7。下一次同主题开放使用新的期别，预告初始0，首次确认重新发当期奖励，重复确认不重发；旧期回执禁止跨期使用。旧期数据保留用于审计，不批量清库。

验证七个活动各自第一、第二、第三轮开放、原生刷新点前后、查询与领奖重传、重建服务、移动本地审核日历，以及日月盈仄的通用/剧情双确认路径。相关现有94项回归通过，新增9项边界用例通过，合计103项。测试只使用临时数据库；活跃存档通过正常查询自修完成确认时间，其他进度和奖励不重置。
