# 做菜活动同名食材串用修复

## 原因与现场记录

用户确认二次神降失败是尚未解锁神器；保留神器前置条件，本次仅修复做菜。

玩家 5 持有本期春卷食材：1290150（小麦）3 个、1290151（蔬菜）2 个。
点击制作提示「食材不足」，没有发出 840 制作请求。该账号还保留上一活动的
1290317 数量 3、1290318 数量 1，因此客户端误用上一活动配方时恰好触发不足。

两套食材名称和图标相同，物品 ID 不同。客户端
`NewYearFoodRecipeView.InitRecipeList`（0x19F08A8）和
`NewYear2FoodRecipeView.InitRecipeList`（0x1A2B848）都按共享表的
`NewYearFood.IsUse == 1` 筛选。当前原表仅配方 25–35（阏逢敛遗）标记为 1，
珠雀绮馔的 1–13 标记为 2。旧活动页面因此显示新活动配方，检查和请求均使用
新食材 ID。两个 `SendCafeStoreCooking` 的材料边界判断本身是 `>=`，没有
「材料必须多一个」的问题，也没有修改其原版成本判断。

## 修复

客户端两个菜谱页面分别绑定对应活动的原版配方 ID 集合，从服务端保存的原表
`ActivityParam2` 与菜谱 `ItemGroup` 生成，保留原来的排序、配方解锁、材料检查
和制作发包。范围判断使用无符号减法，排除 0、另一活动及停用活动的配方。
补丁仅变更两个原生跳转和两个空代码区，不修改材料表、图片、地址或存档管理。

服务端移除用 `ShowRank` 推断制作店铺的限制。该值只是显示排序；客户端两个
制作入口均向当前选中的店铺发送请求，不按该值划分菜品。仍检查本期食材组、
菜谱持有、店铺解锁、厨师和队列容量，并按照原版配方扣料、计时、经验和收入。

打包保留 `X2-Revival-ActivityUI-Local-signed.apk` 和
`X2-Revival-ActivityUI-Remote-signed.apk` 两个发布名称，使用原发布证书签署。
无需迁移库存或把两套同名食材合并；需要安装更新后的客户端才能解决点击前误判。

不足食材的订单整体回滚，不残留订单、不损失已经检查过的小麦。
完整活动运行协议回归共 51 项通过。APK 签名、内容差异检查见本次任务结果；
游戏内由用户验收。
