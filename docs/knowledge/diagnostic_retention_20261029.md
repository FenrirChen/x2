# 诊断记录滚动保留48小时（本地实现与验证）

## 范围

用户批准诊断历史只保留近两天，并要求本地测试后再考虑发布。沿用现有存档ZIP格式与全部102张玩家表结构，不执行VACUUM、不清理账号、不修改APK，不在远程执行删除。

实际清理五张表的过期诊断行：fight_drop_items、fight_drop_claims、battle_shop_purchases、battle_shop_pickups、economy_checkouts。
对fight_drop_observations只将旧decoded/context重复文本置为{}；保留全部父行、原始body、uuid、digest、归属和时间。

battle_unresolved_rewards完全排除；首次代码写入被自动审批拒绝，理由是它可能涉及未结算奖励证据。该次命令未执行，随后采用保留整表的更保守实现。pending_rewards、pending_reward_instances、pending_reward_deliveries均未纳入清理。

## 准入条件

严格早于当前服务器时间减172800秒的才是过期，恰好48小时仍保留。时间为0/NULL、未来时间、不足48小时、缺失归属或生命周期证据均保留。

掉落副本必须有关联且同账号的economy_runs.settled=1。economy_checkouts还需同账号battle_entries.created_at证明年龄。
商店诊断没有run_id，若同账号同关卡仍有未结算运行则保守保留；关卡0在该账号有任何未结算运行时也保留。

不删除battle_entries、battle_receipts、battle_checkout_wire、reward_settlement_audit、任务/活动/赛季事件、商店限购、邮件或强化/洗练数据。因此既有任务修复、限时成就、历史补偿仍可消费原证据，无需先迁移摘要。

## 清理与存档

后台每15分钟扫一轮，启动后自动开始第一轮。使用独立线程拥有的SQLite连接；扫描按rowid键集分批，不对全部账号做一笔大删除。小诊断行每批最多128，可能很大的掉落文本每批最多2行。每批提交后让出调度。
复用导入/checkpoint排他保护与game wait_for_import，避免游戏线程同步等待后台写锁。写入标记必须在主循环提交线程任务之前发布；不能只在线程里设置，否则检查通过后的同步读写事务可能被后台抢先提交，触发SQLITE_BUSY_SNAPSHOT。新增延迟线程启动的确定性测试覆盖这个窗口。另用独立maintenance事件表示排队/运行中的清理任务，与importing事件共同门控wait_for_import；清理完成不清除其他导入任务的标记，已用交接测试覆盖。停止时等待正在运行的清理线程结束，才关闭数据库保护器。无结构变更和额外启动索引。

导出在同一个一致性读快照内按相同规则过滤诊断行/重复文本，不修改数据库；即使后台第一轮尚未完成，也不会再把旧副本装进新存档。原始body仍作为BLOB完整保存并校验。

旧档导入依然先完成全部格式和引用校验，再在内存导入计划中移除过期副本，避免先写入大文本再清空；覆盖前保留单份备份，覆盖事务提交前再次按SQL清理目标账号的过期诊断。清理异常与整个导入一起回滚；其他账号不受影响。导入前备份也采用新导出规则，保留完整必要状态，过期诊断不再作为必备数据。

专项发现并补修：跨账号UUID碰撞时，原_insert_drop_observations只映射报告整数ID，没有映射uuid，导致报告与移植后的economy_runs失联。现传入同一uuid_map同步调整；不新增表/索引或改格式。

## 验证说明

新增专项覆盖截止点、账号隔离、近期/未结束/孤儿/未知时间保护、清理回滚、幂等、后台键集扫描、取消等待线程、旧档回灌、跨账号映射，以及实际战斗结算重发/任务成就查询/下一场战斗。
所有102张存档表使用完整合成状态比对，非清理目标的表和snapshot必须完全一致。
大诊断文本用例：旧格式合成数据包含144MiB重复诊断文本，未过期时按原规则触发128MiB条目限制；过期后导出成功且原始body仍在，虚拟过滤不改变数据库。
旧通用存档测试改用近期商店诊断时间，继续要求完整往返相等；过期数据则用专项单独验证明确的差异，不在canonical_state里隐藏清理损失。

全量单元/集成测试共1640项均有覆盖：1621通过，13失败、6错误。19项全部在未修改基线fbdcbee逐项复现，没有新增失败；包括注册邮件、静态关卡/年兽/顾客测试与缺少外部掉率/语言数据。证据见analysis/diagnostic_retention_20261029/full_validation.json。
最终修改后的存档专项、完整往返、导入任务、并发与HTTP链路共73项全部通过（201.16秒），最终存储/消息分发/清理屏障专项20项通过（38.50秒）。
第一轮50人并发与全量测试同时运行：正确性、清理、0断线/0SQLITE_BUSY通过，但结算P95为4814ms，未达到既定SLO，不将其标成性能通过。第一轮安静环境复核发现上述标记发布竞争窗口，导致结算回13；已补修，保留失败报告而不宣称通过。修复后再次独立压测通过：50客户端，每账号20神格、入场3名神格，2.22GiB合成数据库、1024份过期诊断报告、约24.5MiB存档；300场战斗及600次含重放的结算请求全部完成，50账号获奖，301份结算回执（含历史种子1份）数量准确。
结算P95 100.42ms / 最大303.54ms，入场P95 266.44ms / 最大316.52ms；商店/任务/邮件P95均小于36ms。50人同时登录P95为2950.88ms（不纳入游戏请求2秒SLO）。导出0.829秒、并发导入1.461秒，其中覆盖写入0.297秒。无SQLITE_BUSY、连接超时或超过500ms主循环停顿；quick_check=ok；过期诊断子行和重复JSON均清理完。详见load50_final.json。
该结果仅证明本机合成负载下既定指标通过，不等同于远程硬件或所有真实玩法的性能保证。

## 限制

本轮是保守的诊断瘦身，不是把所有两天前战斗历史删除。必要原包/回执/事件仍会增长；若这些本身超过现有限额，需另做摘要迁移或流式/分块格式方案。不能承诺所有大账号都恢复到某个固定大小。
物理SQLite文件可能仍有空闲页，等待复用；本轮不会自动压缩。线上收益需部署后结合各账号实际结构评估。
