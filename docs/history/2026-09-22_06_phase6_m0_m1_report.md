# Phase 6 — M0/M1 implementation report

Date: 2026-09-22

## Outcome

M0 Workspace and M1 Protocol Core are complete. The repository can encode a registered protobuf message into the recovered X2 frame, incrementally recover that frame from TCP-style byte fragments, verify its request CRC32, and decode it back to the original message values. No APK/native code was executed, no remote endpoint was contacted, and no Login handler or TCP server was implemented.

## Workspace and files

The independent Git repository uses a Python 3.12 src layout. It contains:

- project metadata, ignore rules, change log and research notice;
- architecture, milestones, protocol specification, evidence index and three ADRs;
- separated protocol, network, message and configuration packages;
- unit, fixture and future integration-test directories;
- local fixture generator and packet inspector;
- an external reverse-data index instead of copied APKs, libraries or large reports.

The environment-specific `.venv` and all runtime data are ignored. Configuration uses X2-prefixed environment variables. Standard logging carries connection/message/request context and excludes authentication payloads.

## Architecture decisions

1. Python 3.12 was selected for rapid, inspectable binary-protocol work and later standard-library asyncio support.
2. The early backend remains one deployable service; microservices are deferred until measured need exists.
3. Protocol bytes, network lifecycle and future business state are separate layers. M1 codec code has no player database, authentication or handler dependency.

## Protocol implementation

### PackInt and CRC32

`encode_packint` and `decode_packint` implement signed int32 zigzag followed by the recovered big-endian 1–5 byte prefix format. Tests cover zero, positive/negative values, every width boundary, int32 extrema, non-zero offsets, truncation and invalid prefixes. Request-header `sign` uses unsigned `zlib.crc32(body)` and is explicitly documented as unrelated to fight sign.

### Framing and streams

The frame is implemented as:

```text
PackInt(totalLen) + PackInt(headLen) + protobuf header + PackInt(messageId) + protobuf body
```

`totalLen` excludes its own prefix. Request/response headers use the confirmed protobuf field order. Decoder checks negative/oversized lengths, head length bounds, truncation, trailing bytes, negative IDs and checksum mismatch. `PacketStreamDecoder.feed` handles one packet, three-way fragmentation, two concatenated packets, and a complete packet followed by a partial packet. The 16 MiB maximum is marked `TEMPORARY_COMPAT`, not original behavior.

### Registry and protobuf

The strict registry supports ID→name and name→ID and raises for unknown values. All confirmed M1 IDs are present, and `L2C_CheckoutMainMissionSign` is intentionally absent. A standard-library protobuf-wire subset supports confirmed varint, string, bytes and opaque nested-message fields. Full selected schemas are registered for Login, GuideStep and PrepareMainMission request/response pairs. Login is tested only as serialization data; there is no Login business implementation.

### Session and inspector

`SessionState` stores only connection ID, session ID and last request ID, and emits safe logging context. It does not authenticate or own player state. `packet_inspector.py` reads one local fixture and reports frame/header/message/checksum data; sensitive body field names are redacted. `synthetic_guide_request.bin` is deterministic and explicitly not an official capture.

## Remaining unknowns

- No official packet capture exists; byte compatibility is currently evidence- and fixture-tested rather than live-client-tested.
- Nested Login snapshot messages are opaque in M1, and the minimum valid Login response remains UNKNOWN.
- Fight uuid/sign/data semantics and DropValueID server mapping remain UNKNOWN.
- The recovered decoder's tolerance for non-canonical PackInt representations has not been used as a compatibility requirement; the encoder emits canonical forms.
- The 16 MiB maximum is a defensive temporary choice pending controlled client integration.

## M2 readiness

Ready. Framing, stream buffering, errors, limits, message lookup and safe session metadata can be composed into an asyncio connection loop without changing business code. M2 must retain offline/integration fixtures and must not add Login behavior.
